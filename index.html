01

System Overview

Yorindo handles the complete event lifecycle: contact database management, invitation blasting, participant registration with approval workflows, event-day QR check-in (offline-capable PWA), and post-event analytics with AI-powered insights (YoriMind).

Core Actors

admin
Full platform access — manages users, contacts, events, blasts, reports
staff
Event-scoped — check-in, approvals for assigned events only
viewer
Read-only — events and reports for assigned events
participant
Self-service — registration, ticket management, dashboard

Authentication & Authorization

Login Flow (Phase 2)

1
POST /api/auth/login
Validate credentials → bcrypt.compare password hash
2
Issue tokens
Short-lived JWT access token (15 min) + httpOnly refresh token cookie (7 days)
3
Every API request
Bearer token validated → Redis JWT blacklist check → response
4
Token refresh
POST /api/auth/refresh with httpOnly cookie → validate against Redis → new access token
5
Logout
POST /api/auth/logout → add refresh token to Redis blacklist → clear cookie → authStore.clearAuth()

JWT Payload

{ "sub": "user-uuid", "role": "admin|staff|viewer|participant", "iat": ..., "exp": ... }

Participant SSO

● Phase 1 Mock
  • POST /api/auth/google-mock
  • Simulates Google OAuth pre-fill (name, email only)
  • MockGoogleAuthDialog in frontend
● Phase 2 Real
  • Real Google OAuth PKCE flow
  • Same /api/auth/google endpoint
  • Full token exchange

Key Features & Flows

Contact Upload & ETL Pipeline

1
Admin uploads Excel / CSV
POST /api/contacts/upload (multipart) → file stored in staging directory
2
ETL Worker processes
Parse rows → Normalize via AI (Claude/OpenAI) → compute completeness_score
3
Duplicate detection
Phone-based dedup → flagged records written to flagged_records table
4
Admin reviews flags
Contacts tab Flagged view → resolve (upsert to contacts) or discard

Participant Registration Flow

1
Visit /register/[eventSlug]
Public event landing page loads event details via GET /api/events/public/[slug]
2
Optional Google SSO pre-fill
MockGoogleAuthDialog → name + email pre-filled (read-only). Phone always entered manually.
3
Multi-step form submission
Contact Info → Survey → Confirm → POST /api/registrations → status: pending
4
Double opt-in via email
Participant clicks confirm link → GET /api/registrations/confirm/:token → status: confirmed
5
Participant session created
Auto-trigger POST /api/auth/google → participant accessToken set → "Masuk ke Dashboard" shown

QR Check-in — Offline-first PWA

1
Staff opens Scan PWA
GET /api/scan/participants/:eventId → participant list cached in IndexedDB
2
Online scan
Scan QR → POST /api/scan/verify → validate token → UPDATE registration status: attended
3
Offline scan
Match QR against IndexedDB cache → queue scan → Background Sync registered
4
Sync on reconnect
Background Sync fires → POST /api/scan/offline-flush → batch upload queued scans

YoriMind AI Analysis

Admin requests analysis for a completed event via POST /api/yorimind/analyze. Claude Sonnet API processes attendance data, demographics, and engagement metrics to return structured insights:

root_causes recommendations summary

Recommendations are prioritized as high / medium / low. Analysis is only available for events in completed status.

Development Approach

● Phase 1 — Mock-first
  • All API calls intercepted by MSW v2 handlers
  • In-memory repositories — no real DB
  • Everpro, Brevo, Claude API all mocked
  • Story 1.4 (OpenAPI spec) is the gate before Epic 2+
  • Story 1.8 is the Phase 1 BE gate
● Phase 2 — Real Backend
  • Swap to PostgreSQL/MongoDB repos
  • Swap mock adapters for real (Everpro, Brevo)
  • Redis for JWT blacklist + BullMQ
  • Real Google OAuth replacing /api/auth/google-mock
